# Google Play release — LEVEL UP for Android

Single place for: what the Android build guarantees, how to build and check it, the Play Console answers (derived from what the
code does), and what only the owner can do. Build commands and signing are in [`mobile/README.md`](../mobile/README.md); store
text and graphics in `mobile/store/`.

App: `app.levelup.learn3d` (permanent), `versionName 1.4.1` / `versionCode 7` (raise `versionCode` for every upload),
minSdk 23, **targetSdk 36, compileSdk 36**, Android Gradle Plugin 8.10.1, Gradle 8.11.1, **JDK 21** (Capacitor 7 generates
Java 21 settings in `android/app/capacitor.build.gradle`; JDK 17 will not build it).

## 1. Target API level

Google Play: "New apps and app updates must target Android 16 (API level 36) or higher to be submitted to Google Play" (mobile),
from 31 August 2026; an extension to 1 November 2026 could be requested. Existing apps must target API 35+ to stay available to
new users on newer Android versions.
Source: <https://support.google.com/googleplay/android-developer/answer/11926878> (read 2026-10-11).
The app is already at 36. The page publishes the next step each year; re-read it every summer (the 2027 level was not published
when this was written).

What targeting 36 means for this app (Android's own docs):
- Edge-to-edge is enforced on Android 15+, and on Android 16 the opt-out (`windowOptOutEdgeToEdgeEnforcement`) is "deprecated
  and disabled" (<https://developer.android.com/about/versions/16/behavior-changes-16>). Handled in `MainActivity.java`, section 4.
- Predictive back is on by default on Android 16 and `onBackPressed` is no longer called (same page). Capacitor's App plugin
  registers through AndroidX's back dispatcher, so the JS back handler keeps working.
- No orientation lock or fixed size in the manifest, so the Android 16 large-screen rule needs nothing: for apps targeting 36,
  "orientation, resizability, and aspect ratio restrictions no longer apply on displays with smallest width >= 600dp"
  (same page); the app simply fills a tablet or foldable.
- No native libraries in the AAB (the 1.4.1 AAB had no `.so` files), so Play's 16 KB page-size rule has nothing to apply to.

## 2. Release build

```bash
npm run mobile:build && npx cap sync android     # web bundle -> android/app/src/main/assets, regenerates capacitor.config.json
cd android && ./gradlew bundleRelease            # app/build/outputs/bundle/release/app-release.aab  (upload this)
```
`android/keystore.properties` (never committed) holds the upload key. Without it Gradle prints a WARNING and the release is
**unsigned** — Play rejects it.

Lean release (`android/app/build.gradle`, `proguard-rules.pro`, `res/raw/keep.xml`):
- `minifyEnabled true` + `shrinkResources true` (R8). The unshrunk 1.4.1 dex was 7.0 MB (androidx, Kotlin stdlib, appcompat).
  An R8 dry run with these rules on the same libraries produced a 0.9 MB dex, with Capacitor's core, `AppPlugin`,
  `HapticsPlugin` and their `@PluginMethod` methods kept by name. The real size comes from the build (section 7).
- Capacitor finds plugins by class name and calls methods by reflection, so `proguard-rules.pro` keeps `com.getcapacitor.**`,
  `com.capacitorjs.plugins.**` and Cordova's bridge classes. **A plugin added later needs no new rule** (they are covered), but
  check that `app/build/outputs/mapping/release/missing_rules.txt` is absent or only suggests `-dontwarn` lines.
- `res/raw/keep.xml` stops the resource shrinker removing `res/xml/config.xml` (generated by `cap sync`, read by name by the
  Cordova bridge).
- The mapping file is embedded in the AAB, so Play Console de-obfuscates crash stack traces by itself (file names and line
  numbers are kept).

## 3. Privacy and attack-surface settings (and why)

| Setting | Value | Why |
|---|---|---|
| `allowBackup` + `dataExtractionRules` | `false`, cloud backup **and** device transfer excluded | Games and the optional Supabase session live in the WebView's local storage. Auto Backup would copy them (including the sign-in session) to Google Drive and to a new phone. The privacy story is "local, plus an opt-in owner-only backup"; this keeps it true. Android 12+ may still run device-to-device transfer with `allowBackup="false"` on some devices, so the rules file excludes it explicitly ([Auto Backup docs](https://developer.android.com/identity/data/autobackup)). Cost: moving to a new phone needs the in-app account backup (or *Settings → Backup*, the file export). |
| `usesCleartextTraffic` | `false` | HTTPS only. The CSP already allows only `'self'` and the Supabase project. |
| Permissions | declared: `INTERNET`; merged from `@capacitor/haptics`: `VIBRATE`; androidx adds a signature-level `…DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` | `INTERNET` only for the optional account. No storage, camera, microphone, location, contacts or notification permission. |
| FileProvider | cache + the app's own `Pictures/` only | Capacitor's template shared the whole external storage root; nothing in the app uses the provider (no camera input). |
| Backup file hand-off | `FilesPlugin` writes the backup text to the app's private cache and opens Android's share sheet | The WebView has no Web Share API for files (MDN browser-compat-data: `navigator.canShare` is unsupported in Android WebView) and Capacitor 7 sets no download listener, so a `<a download href="blob:…">` click is dropped; so *Settings → Backup → Export my games* would otherwise do nothing in the app (`mobile/src/native.ts` routes that click to the plugin; the page is unchanged). No storage permission; nothing leaves the phone unless the user picks a target. |
| WebView | file access off, geolocation off, debugging off, mixed content off | `MainActivity.hardenWebView`, `capacitor.config.ts`. Content access stays on: the file chooser (notes import, backup import) returns `content://` URIs. |
| Native HTTP/cookies | `CapacitorHttp` and `CapacitorCookies` disabled | Their native requests bypass the page's CSP. Note: Capacitor registers those core plugins unconditionally, so the CSP is not a hard network boundary against an injected script; the "no request while signed out" rule is held by the app's code and tested. |
| CSP (`mobile/index.html`) | `connect-src 'self' https://<project>.supabase.co`, `object-src 'none'`, `base-uri 'self'` | Unchanged; now covered by `tests/unit/android-shell.test.ts`. `script-src 'unsafe-inline'` stays: Capacitor injects its bridge as an inline script on WebViews without `DOCUMENT_START_SCRIPT`. |

`tests/unit/android-shell.test.ts` fails if any of this regresses (manifest, permissions, release shrinking, target API, CSP,
Capacitor config, back-button rules).

## 4. Edge-to-edge, keyboard, back button

- **Android 15+ (targetSdk 36)**: the window is drawn behind the status bar, gesture bar and camera cut-out, and Capacitor 7 does
  not inset the WebView by default (its `adjustMarginsForEdgeToEdge` default becomes `auto` only in Capacitor 8), and how far
  the WebView reports `env(safe-area-inset-*)` depends on its version, so the app does not rely on it.
  `MainActivity.fitSystemBars` therefore gives the WebView
  margins for system bars + cut-out + **keyboard** (an edge-to-edge window is no longer resized by `adjustResize`), and the
  page keeps its own `env()` padding, which is then 0. Android 14 and older keep their normal opaque bars and are untouched.
- Colours behind the transparent bars and the light/dark status-bar icons: `MainActivity` starts with the system light/dark mode;
  the page then tells the shell what it is showing (`mobile/src/system-bars.ts` -> `SystemBarsPlugin`): the in-app theme from
  Settings, the system mode, and the 3D play screen, which is always dark. The two colours are the page backgrounds in
  `src/app/globals.css`; a unit test fails if the CSS, the TypeScript and `MainActivity.java` drift apart.
- **Back button** (`mobile/src/native.ts`, rules in `mobile/src/back.ts`): in a game the game decides; elsewhere one screen back
  (or to the library when there is no history); on the library the app moves to the background. Android 12+ does the same for a
  root launcher activity and recommends not finishing it
  ([behavior change](https://developer.android.com/about/versions/12/behavior-changes-all)); the old `exitApp()` killed the warm
  start.
- Splash: white `splash.png` on the launch theme (unchanged). On a dark system it flashes white before the dark page; a dark
  launch theme (`values-night`) is a possible later polish.

## 5. Play Console answers, derived from what the code does

**Does the app collect data?** Yes, but only when the user creates the optional account (Settings → Account): the app
makes no network request while signed out (tested with the network blocked). Google's definition: "Collect means transmitting data
from your app off a user's device", including by webviews you control
([Data safety help](https://support.google.com/googleplay/android-developer/answer/10787469)). Everything that is sent goes to one
service provider, the project's Supabase backend (`mobile/src/cloud/`), over HTTPS.

| Play data type | Collected | What (code) | Purpose | Optional | Shared |
|---|---|---|---|---|---|
| Personal info → **Email address** | yes | `auth.signUp / signInWithPassword` (`cloud/account.ts`) | Account management | yes | no |
| Personal info → **User IDs** | yes | Supabase user UUID, the `user_id` of every row | Account management, App functionality | yes | no |
| App activity → **Other user-generated content** | yes | games: title and the generated game spec (built from the user's notes) (`cloud/api.ts`) | App functionality (backup, sync) | yes | no |
| App activity → **Other actions** | yes | play sessions (progress, answers, score) and the review deck | App functionality (backup, sync) | yes | no |

Not collected: location, financial info, health, messages, photos/videos, audio, files and docs (the notes file and the backup
file are read on the device only), contacts, calendar, web browsing, crash logs/diagnostics (no SDK; Play's own Android vitals
are Google's, not the app's), device or other IDs (no advertising ID, no installation ID), search history, installed apps. There
are no ads, analytics or third-party SDKs besides Supabase's client library.
- **Shared with third parties: No.** Supabase processes the data on the developer's behalf and instructions, which Play does not
  count as sharing.
- **Encrypted in transit: Yes** (HTTPS only; cleartext disabled).
- **Users can request deletion: Yes**: in-app (Settings → Account → delete my account and cloud data) and on a web page.
- "Optional" is allowed here because every user can use the whole app without an account.
- **Android Auto Backup is off**, so the OS does not copy app data to Google; nothing to declare for it.
- The Data safety form must match the privacy policy (`mobile/store/privacy-policy.md`, updated for the backup change).

**Data deletion** (required because users can create an account). Play requires an in-app path and a public web link where
users can request deletion "on the web page itself" (not by sending them back to the app); the page must name the app or
developer as in the store listing; any retained data must be explained
([account deletion help](https://support.google.com/googleplay/android-developer/answer/13327111)). `mobile/store/account-deletion.md`
covers it; add a working `mailto:` link or form at the top and the exact store app name.

**App access (reviewers).** Login is optional and every feature of the app works without it, so choose "all functionality is
available without special access". Because the account is a visible feature, also give reviewers a ready account in English
(<https://support.google.com/googleplay/android-developer/answer/15748846> asks for reusable, always-valid details): create a
confirmed test user in Supabase (or turn *Confirm email* off) and paste the e-mail and password plus "sign-in is optional, under
Settings → Account".

**Content rating** (IARC questionnaire). Educational/learning app with 3D mini-games: no violence (the code has no combat or
damage mechanics; "boss" stations are quiz challenges), no sexual content, no gambling, no profanity, no user-to-user
communication or sharing, no location sharing, no digital purchases, no unrestricted web access. Answer truthfully; expect the
lowest rating. User-generated content: users only see their own notes and games.

**Target audience and Families policy — owner decision.** The privacy policy says the app suits "learners of all ages". If
children (under 13 in most places) are a target audience, Play's Families policy applies: apps must comply with COPPA/GDPR,
"disclose the collection of any personal and sensitive information from children", and treat authentication information as
sensitive ([Families policy](https://support.google.com/googleplay/android-developer/answer/9893335)). The optional account collects
an e-mail address, so `listing.md`'s old "no data collection" line is not true for children who sign up. Simplest safe choice: set
the target audience to 13+ (or older) in Play Console; if you want under-13s, get legal advice first (parental consent, or a
build without accounts).

**Ads**: no. **In-app purchases**: no (paid features later must use Google Play Billing, never Stripe). **Government/news/health/
financial declarations**: none.

## 6. What needs the owner

1. Upload key + Play App Signing; keep `keystore.properties` and the `.jks` backed up and private.
2. Fill in the support e-mail in `privacy-policy.md` and `account-deletion.md`, host both at public URLs, paste them in Play
   Console (privacy policy, Data safety → deletion link).
3. Decide the target audience (section 5). Fill Data safety exactly as in the table; content rating; ads = no.
4. Create the reviewer test account and fill *App access*.
5. Supabase dashboard (can't be done from the repo): *Confirm email* / Site URL, own SMTP before many sign-ups, password reset is
   not built in (see `mobile/store/release-checklist.md` 2b).
6. Store listing: text in `mobile/store/listing.md`, icon, feature graphic, at least 2 phone screenshots (tablet screenshots
   recommended); regenerate with `node mobile/shots.mjs`.
7. Testing: internal track first. A personal developer account created after 13 Nov 2023 needs a closed test with at least 12
   testers opted in for 14 continuous days before it can apply for production
   (<https://support.google.com/googleplay/android-developer/answer/14151465>); the help page states it for personal accounts, so check the Dashboard for what applies to
   yours. Read the Pre-launch report.
8. After the first upload the package name and the upload key can never change.

## 7. In the real build (checklist)

Build: `npx cap sync android && cd android && ./gradlew bundleRelease` (then `assembleRelease` to sideload).
1. Build passes with R8 (no "Missing classes" error). If `app/build/outputs/mapping/release/missing_rules.txt` appears, add the
   suggested `-dontwarn` lines to `proguard-rules.pro`.
2. Merged manifest (`app/build/intermediates/merged_manifests/release/processReleaseManifest/AndroidManifest.xml`): permissions
   are exactly `INTERNET`, `VIBRATE` and `…DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`; `allowBackup="false"`,
   `usesCleartextTraffic="false"`, `dataExtractionRules` present; no `debuggable`.
3. AAB: signed; contains `proguard.map` (`unzip -l app-release.aab | grep -i map`); no `.so`; compare size with 3.65 MB (1.4.1).
   Mapping keeps `com.capacitorjs.plugins.app.AppPlugin` and `HapticsPlugin` unrenamed.
4. On a phone with the release APK, `adb logcat | grep -iE "capacitor|plugin"` shows no "plugin not found / not implemented".
5. **Android 15 or 16** (device or API 35/36 emulator): header is below the status bar, bottom controls above the gesture bar, both
   orientations (and a cut-out phone); focus the notes box on *New game* and the e-mail/password fields in Settings → the keyboard
   does not cover them; rotate with the keyboard open; switch system dark/light while the app is open, and set the in-app theme
   (Settings) opposite to the system, then open a game: the strip behind the status/gesture bar matches the screen (always dark in a
   game) and the clock/battery icons stay readable.
   If this is wrong, remove the `fitSystemBars(webView)` call in `MainActivity.onCreate` to go back to the old behaviour.
6. **Android 13/14**: looks exactly as before (status bar readable, keyboard resizes the page).
7. Back button: library → leaves to the background (app resumes warm); other screens → back one; game → panel → pause → leave.
8. File import still works (*New game → load a .txt/.md*, *Settings → Backup → Import from a file*) — the WebView file settings changed —
   and **backup export opens the share sheet** (*Settings → Backup → Export my games*): save it to Drive/Files, then re-import it. If the share
   sheet does not open, check `adb logcat` for "LevelUpFiles" / FileProvider errors.
9. WebGL game plays, sound, vibration setting, the optional account (sign up/in, sync, delete) over HTTPS.
10. `adb shell dumpsys package app.levelup.learn3d | grep -i backup` shows no allowed backup; `adb backup` yields nothing.
11. `npm run test:e2e:mobile` (web bundle only; native behaviour is covered by the list above).
