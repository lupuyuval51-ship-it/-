# LUPU-FIT — Engineering decisions

Ambiguities are resolved toward the safer, more private and more honest option.

## D1. Location in the repository
The repository root already holds an unrelated flat-file project (LEVELUP AI, with its own `package.json`
and `AGENTS.md`). To avoid overwriting it, LUPU-FIT lives in `lupu-fit/`, which is its own npm workspace root.
`AGENTS.md` at the repo root documents the LEVELUP project and was not applied to LUPU-FIT.

## D2. Colour tokens changed after `contrast-check` failed the specified palette
The specified palette does not meet the specified targets, so the tokens were adjusted rather than the check relaxed:
- `--on-primary` `#0B0B0D` → `#000000`: `#0B0B0D` on `#FF6A00` is 6.85:1 (< 7:1 required); `#000000` is 7.31:1.
- Light `--success` `#1F7A4C` → `#1D7447`: 4.48:1 on `--surface-2` (< 4.5:1); now 4.85:1.
- New `--tally-active` token (dark `#FF6A00`, light `#B33F00`): `#FF6A00` is only 2.55:1 / 2.87:1 against the light
  background / surface (< 3:1 for non-text UI). The TallyMarks active mark uses this token. The orange CTA fill
  itself is exempt from a fill-vs-background ratio because its label meets 7:1.

## D3. Achievement id `week_streak` → `two_week_streak`
"Week streak" was ambiguous. Defined as: weekly goal met in 2 consecutive weeks; `month_streak` = 4 consecutive weeks.

## D4. Readiness reducer
`score = sleep + energy + (6 − soreness)` (3..15). `≤5` → `rest`, `≤9` → `easier`, else `normal`.
Reported pain can never yield `normal` (floor `easier`) but does not force `rest` alone.

## D5. Carbohydrate floor (130 g)
Order of adjustment when carbs < 130 g: fat → its 25% floor, then protein → no lower than 1.2 g/kg of reference
weight, then **raise kcal** to fit 130 g. kcal is never lowered, so adult floors and the minor no-deficit rule
stay valid. A `carb_floor_raised_kcal` note is emitted so the UI can explain it.

## D6. Allergen filter is deliberately over-inclusive
Err toward hiding. Examples: hummus → sesame; wrap/tortilla → gluten; `חמאת בוטנים` hides for peanut but not dairy
(plant "butter"/"milk" exceptions) because the nut allergen still matches. `חלבון` ("protein") is not milk.
Structured `allergens[]` tags are always UNIONed with keyword detection; the UI must always show the verification
disclaimer.

## D7. Safety classifier scope
Deterministic first-line shield, not a clinical guarantee (stated in the source). Negation within ~3 tokens
(`no chest pain`, `אין כאב בחזה`) suppresses a hit. PED rules require BOTH a substance term and dosing/cycle intent,
and are suppressed for cortisone/inhaler/topical contexts. Literal first-person phrases such as "I want to die"
always trigger even if jokingly meant — a false positive costs a gentle message, a false negative costs far more.

## D8. Where Node-dependent tests live
`shared/src` must contain no Node/DOM globals, so its tsconfig has `types: []`. Tests that spawn the linters need
Node and live in `scripts/` with their own tsconfig (`npm run test:tools`).

## D9. Dependency advisory
`npm audit` reports a moderate advisory on `vitest@3` (`@vitest/mocker`, dev-only; affects the vitest dev server
mock-redirect feature, not shipped code). Upgrading to vitest 5 is a breaking change; deferred, not hidden.

## D10. Technique videos are generated in code (schematic, not filmed)
`npm run gen:videos` renders every exercise as a silent, seamless 8 s loop (720x720, H.264 High, +faststart, ~30 fps,
poster JPG ≤ 60 KB) from a parametric skeleton: forward kinematics + two-bone IK, motion programs per movement family
(`scripts/video/motions*.ts`), ids mapped by `scripts/video/classify.ts`. The primary muscle is highlighted and the
start/end poses are shown as a faint ghost. This is a stylised illustration, NOT footage of a person.
- Each clip carries `fidelity` in `media-manifest.json`: `specific` (a motion written for that movement, 182; see the v2 addendum for current counts),
  `approximate` (nearest family; a variant looks like its sibling, 62) or `generic` (pattern fallback, 0).
- All manifest entries have `reviewed: false`. Nothing here is human-reviewed; a coach should review before the UI
  presents a clip as an authoritative demonstration. The spec rule "never claim a video exists unless a validated,
  reviewed record exists" therefore still applies: set `reviewed` only after human review.
- Known limits: side view only (movements in the frontal plane, e.g. flies, wipers, clamshells, are approximated or shown
  from the front); no hands or fingers; equipment is drawn as simple symbols; unilateral exercises alternate sides.
- Generated media is not committed (`client/public/media/` is git-ignored, ~41 MB). Build pipelines run `gen:videos`.
- Quality gates: `scripts/video.test.ts` checks for every exercise that bone lengths never change, nothing sinks through
  the floor, no joint teleports between frames and the loop is seamless; `npm run verify:videos` re-validates every file
  with the repo's own MP4 validator AND ffprobe and checks sha256 against the manifest.
- IK bend side is chosen once per limb (at its most flexed sample) and locked for the clip. Choosing per frame from a
  world-space preference made elbows/knees flip mid-motion; the invariant test caught it.

### D10 addendum: v1.1 improvements
Larger figure (far cable/band anchors no longer shrink the camera), hands, a floor surface with a contact shadow, a rep counter
(4 dots) for rep/cycle clips and a progress bar for holds/stretches, a short pause at both ends of every rep, and distinct
motions for movements that previously looked identical (assisted/regular/shrimp pistol, single-leg/elevated/banded bridge,
sumo vs conventional deadlift). Specific-fidelity clips rose from 182 to 185; the rest remain labelled `approximate` and
nothing is human-reviewed (`reviewed: false`).

### D10 addendum: v2 quality pass (generator `procedural-schematic-v2`)
- **Counts**: specific 185 -> 213, approximate 59 -> 31 (generic 0). 29 clips became specific (cable/band flies and crossovers x4, machine and band chest press, wrist and reverse wrist curl, towel/table isometric curl, plain crunch, hollow body rock, sissy/hack/Spanish squat, nordic curl, cable pull-through, kettlebell swing, medicine-ball slam (it was drawn as a kettlebell), thruster, high knees, broad jump, back extension machine, wall angel, wall slide, inchworm, sled push, ring and parallette push-up). `prone_ytw_raise` was downgraded to approximate (it shared the Y-raise motion). Still approximate (31): frontal-plane movements that a side view cannot show (wide/archer/pseudo-planche push-ups, pec deck and reverse pec deck, rear-delt flies, upright row, cuban press, prone T/snow-angel/superman-pull/lat-pull, arm circles, band pass-through, oblique crunch, heel touches, windshield wipers, Russian twist, fire hydrant, clamshell, hip abduction machine, thread the needle, 90/90, turkish get-up, wall walk/handstand hold, isometric towel wring, see the list at the end of `docs/exercise-video-list.md`). Specific means "a motion path written for this movement", not "verified by a coach": every entry is still `reviewed: false`.
- **Anatomy fix (largest defect found)**: elbows and knees could bend backwards in about 45 clips (every pull-up variant, inverted/TRX row, face pull, overhead triceps extension, skull crusher, pistol/shrimp/Bulgarian free leg, single-leg bridge, lying leg curl, ...). IK now forces the flexion side from the joint type (knee left / elbow right of the base-end line for a figure facing +x) and FK limbs clamp to flexion only. Prone exercises are authored face-down (head toward +x). A geometry test asserts no hyperextension for all 244 clips.
- **Look**: no text, rep dots or progress bar in the video (not translatable); muscle highlight is an inset orange capsule on the working segment; a faint dotted orange line shows the path of a held implement; barbell with far plate and sleeve, dumbbell with two heads, cable handle and pulley, pull-up bar with post, medicine ball; limbs stay off-white, orange only marks the working muscle or implement path.
- **Timing**: bilateral rep clips show 2 slow reps per 8 s loop (about 1.2 s up, 0.8 s pause at the top, 1.2 s down, 0.5 s at the bottom); unilateral clips show 4 reps (2 per side, half-length pauses); the profile is eased (smoothstep) and a test checks the pauses and continuity.
- **Budget**: 40.9 MB total (limit 55), priority-A 9.6 MB (limit 12), largest clip 0.41 MB, posters <= 29 KB; H.264 High, yuv420p, faststart unchanged; `verify:videos` 0 errors.
- **Known remaining defects**: no feet-sliding invariant (feet are IK-planted by construction but not tested); figures are very small in prone and overhead clips; front-view clips have no seated variants; pull-up grip width/orientation not distinguishable from the side; hand/finger detail absent. Review tooling: `scripts/video/review-sheet.ts` (contact sheets from the encoded files) and `review-live.ts` (fast renders without encoding).

## D11 — Portable API core instead of Express in the worker
`createApiApp(deps, router).handle(ApiRequest)` is framework-agnostic; Express is an adapter. Device Mode runs the same core in a Web Worker over PGlite. JSON bodies are canonicalised by a JSON round trip. Deviation from literally running Express in the worker.

## D12 — No pg_trgm; content lives in code
Search is client-side over static content in `shared/src/content`. Dishes/templates derive macros/allergens from foods.

## D13 — Offline identity cache
The service worker keeps a last-known copy of `GET /api/auth/me` and `/api/profile` only, served only when the network fails; wiped on logout or 401. All other API calls are never cached.

## D14 — Second UX pass
Per-screen redesign by five parallel owners following `docs/UX_GUIDE.md` (one primary action per screen, sticky action bars on phones, skeletons, collapsed secondary content). Orange is reserved for the primary action and active states.

## D15 — Username + user-chosen password, no e-mail
Accounts use a username (3-24 chars: a-z 0-9 _ . -, case-insensitive) and a password the user picks. No e-mail is collected, so password reset was removed (migration 0003 renames users.email -> users.username; password_reset_tokens kept, unused). Trade-off: a forgotten password cannot be recovered. A one-time recovery key shown at registration is the suggested follow-up if recovery is wanted.

## D16 — "More languages": on-demand machine translation of the UI
Settings > Language keeps Hebrew (RTL, default) and English as the only built-in, fully reviewed languages and adds "Translate the app to another language" (about 70 languages by endonym and English name, plus a free-text language name; ar/fa/ur/yi/ps/ckb and other RTL codes set `dir=rtl`).
- **Source**: the merged English dictionary (all `features/*.ts` keys except `legal.*`, which is never machine translated) is sent in batches of at most 150 keys to the new authenticated `POST /api/i18n/translate` (`{ target:{code,name}, keys }`). It uses the existing `AiProvider` (Claude preferred, Gemini fallback; `complete` gained optional `maxTokens`/`json`). The prompt demands strict JSON with identical keys, untouched `{placeholders}`, no markup, brand/unit names kept. The server validates every value (non-empty, exact placeholder bag, no markup), retries only the bad keys once, then falls back per key to English and lists them in `fallback`. The client re-validates placeholders before storing and never stores fallbacks as translations.
- **Limits**: shares the `coach_usage` ledger (kind `translate`, 30/min and 150/day per user, `429 quota_exceeded` with `Retry-After`); provider overload maps to `429 ai_busy`; no provider returns `503 ai_unavailable` and the UI says "Translation needs an internet connection and an AI service". Nothing is ever fabricated. In Device Mode this works only when an AI proxy (`VITE_AI_PROXY_URL`) is configured; the existing egress guard is unchanged.
- **Cache**: IndexedDB (`idb-keyval`, key `lf-i18n:<code>`) with a whole-dictionary hash plus a per-key source hash. An unchanged app costs zero network calls and works offline; after an app update only new/changed/previously failed keys are re-translated. Every finished batch is saved, so cancel or failure keeps progress and retry resumes. Downloaded languages are listed for one-tap switching and deletion.
- **Activation**: `lf_lang=<code>` plus `lf_lang_custom={code,name,dir}`; `<html lang dir>` follows. English is the per-key fallback. `useLang().lang` stays `'he'|'en'` (`'en'` while a custom language is active) so every existing screen keeps working; new `custom` meta on the context identifies the custom language.
- **Server copy**: `profile.language` stays `he|en` (set to `en` while custom is active). The coach request accepts an optional `uiLanguage {code,name}` (name restricted to letters/digits/space) and the coach prompt then replies in that language; omitting it is unchanged. The deterministic rules-coach fallback and safety messages stay English/Hebrew.
- **Numbers/dates**: `fmt.date` uses the custom BCP-47 locale when the browser supports it; numbers stay Latin digits by design.
- **Limitations**: quality is machine quality and unreviewed (shown in the UI); content names (exercises, foods, dishes) and server-generated plan/menu text are not translated; no per-language fonts are bundled (system fonts render scripts).

## D17 — Configurable Gemini model chain
`GEMINI_MODELS="model-a,model-b"` (server env, first = preferred, falls back on 429/503) overrides the default `gemma-4-31b-it, gemma-4-26b-a4b-it, gemini-2.5-flash, gemini-2.5-flash-lite` (Gemma 4 IDs per ai.google.dev/gemma/docs/core/gemma_on_gemini_api; JSON mode is not documented for Gemma, so responseMimeType is dropped for gemma-* and output is validated server-side). The API key stays in `GEMINI_API_KEY` (server env only, never in the repo or client). Verify any new model supports `systemInstruction` and JSON mode on the Gemini API before using it for translation/coach; the code does not check that.


## D18 - Optional on-device Gemma 4 (LiteRT-LM), cloud stays default
- **Why LiteRT-LM**: it is the documented runtime for Gemma 4 `.litertlm` files with a stable Kotlin Android API on Google Maven (`litertlm-android:0.19.0`, minSdk 24, arm64-v8a + x86_64). The model card calls the MediaPipe route maintenance-mode; AICore/Gemini Nano is device-dependent and not version-pinnable (a possible future provider).
- **Not bundled**: the model (2,588,147,712 bytes) is downloaded after install on explicit user action, resumable, SHA-256 verified before it is marked installed. The default source is the public, non-gated `litert-community/gemma-4-E2B-it-litert-lm` file pinned to a commit; `VITE_LOCAL_MODEL_URL/SHA256/SIZE` override it. No credential exists in the repo or app.
- **Placement**: a decorator at the `AiProvider` seam inside the Device Mode worker (`LocalFirstAiProvider`), bridged to the native plugin through the main thread. All routes keep their own safety shield, quotas, anonymised snapshot, minors caps and rules fallback; the local path cannot bypass them. Deviation: `main.tsx` gets one call (`attachLocalAiBridge`) and `deviceWorker.ts` builds `deps.ai` through a getter so AI stays "unconfigured" (rules coach / 503 translate) unless a proxy exists or local is selected.
- **Policy**: Auto (local only if installed and the user downloaded it, cloud fallback), Cloud only, On-device only (never contacts the cloud; failure ends in the rules coach). 30 s first-token budget, 150-word clamp, hard token caps (coach 320, translate 1024).
- **CPU only, arm64 only, ~6 GB RAM**: GPU is skipped because a native driver crash cannot be caught; supported=false carries a human reason.
- **Packaging**: Kotlin Gradle plugin added for the plugin; ABIs not filtered (Play splits per ABI); `ACCESS_NETWORK_STATE` added for Wi-Fi-only; no foreground service.
- **Unverified on a device** (see docs/ANDROID.md).

## D19 - On-device model removed; AI is cloud only and automatic
- **Decision (user request)**: the optional on-device Gemma 4 (LiteRT-LM) feature of D18 is removed end to end (JS `client/src/ai/local`, Profile AI card, `ai.mode` and "translate locally" settings, `LocalAiPlugin.kt`, the LiteRT-LM dependency, the Kotlin Gradle plugin, `ACCESS_NETWORK_STATE`, `VITE_LOCAL_MODEL_*`). Git history keeps D18 for reference.
- **AI now**: no user-facing AI settings. The hosted server uses Claude when `ANTHROPIC_API_KEY` is set, otherwise the Gemma 4 -> Gemini fallback chain configured by `GEMINI_MODELS` / `GEMINI_API_KEY` (D17) (`server/src/ai/providers.ts`). Device Mode uses the optional `VITE_AI_PROXY_URL` proxy exactly as before D18. When no AI is configured the existing `aiAvailable` / `ai_unavailable` handling shows an honest message and the deterministic rules coach answers. Coach safety shields and the "more languages" translation (D16) are unchanged.
- **Proxy requirements (hard, not met yet)**: no proxy is implemented in this repository and `VITE_AI_PROXY_URL` must not be set for a public release until one meets all of these. The proxy URL ships as a plain string in the APK, the client sends the full provider input with no credential, and the quotas (D16), the 600-token cap, the minors clause and the safety shield run on the phone, so without them the proxy is an open relay for the operator's provider keys. The proxy must (a) enforce its own per-install and global rate and budget limits, (b) ignore client-supplied `system` and `maxTokens` and use fixed server-side prompts and caps per route, (c) cap input and photo size, and (d) verify a Play Integrity token; `client/src/device/proxyAi.ts` must send that token and use `redirect: 'error'`. Details: docs/ANDROID.md "Optional: AI coach proxy".
- **Size**: the AAB no longer carries the ~49 MB of LiteRT-LM JNI libraries and the Kotlin runtime, so it is smaller.

## D20 - Local automations: opt-in reminders and small in-app helpers
- **Scope (user request: "full of automations", then "improve the app")**: only behaviours that are automatic, safe and local. Nothing is sent to a server, no account or push service is needed, nothing needs a permission except reminders.
- **Reminders (all default OFF)**: workout days (weekdays suggested from `daysPerWeek`, editable), meal logging (breakfast/lunch/dinner), weekly weigh-in, "streak at risk" evening nudge, rest-day recovery tip; quiet hours 22:00-07:00 (editable) drop any reminder whose time falls inside them. Copy is short, gender-neutral and makes no medical claims. Minors (age <= 17) get no meal/calorie or weigh-in reminders and the card says so (AGENTS.md minors rule; the Home check-in also omits weight for minors).
- **Permission**: asked only from the tap that turns the first reminder on (`requestPermission()` prompts only when still undecided; a denied state is explained, not re-prompted). The runtime never asks.
- **Delivery**: Android uses `@capacitor/local-notifications` with inexact alarms (no `SCHEDULE_EXACT_ALARM`); a delayed reminder is accepted over an extra sensitive permission and Play declaration. Web uses `Notification` only while open and says so (no push server exists; adding one would collect tokens and break the "no data leaves the device" data-safety answer).
- **Scheduler is a pure function** (`computeTriggers(settings, now, profile, workoutDoneToday)`), unit-tested for quiet hours, weekdays, minors, idempotence, ids and DST (Asia/Jerusalem). Wall-clock times use the local `Date` constructor; repeating rules are handed to the OS as weekday+hour+minute so the OS keeps local time across DST/time-zone changes. "Streak at risk" is state-aware, not static: the one-shots are rebuilt whenever sessions change, and today's is dropped if a workout is finished or in progress; if the user does not open the app, tomorrow's nudge may still fire (an honest limit of local notifications, which cannot run code at fire time). The workout reminder gets the same treatment for today (one-shot next week, repeat re-armed on next open).
- **In-app automations**: auto-rest timer already existed (`logSet` started the rest timer when `restSec > 0`); added only a toggle (default ON = existing behaviour). Weekly check-in banner on Home (last week's workouts vs goal, logged weight change, link to Progress; week starts Sunday in Hebrew and Monday in English; dismissed per week in localStorage; default ON). Monthly backup reminder in Device Mode only (default ON; first reminder 30 days after the first open; export/share through the existing Backup panel or a snooze postpones it 30 days).
- **State**: `localStorage` key `lf_automation_v1:<userId>` (settings), `lf_auto_checkin_seen`, `lf_auto_backup`. Settings are per account so a shared browser does not inherit another user's reminders; logout cancels all pending notifications.
- **Shared files touched (additively)**: `App.tsx` (mounts `AutomationRuntime`), `Profile.tsx` (one import + one card), `Home.tsx` (one import + one banner line), `LiveSession.tsx` (reads the toggle), `BackupPanel.tsx` (records a successful export), `restTimer.ts` (uses the shared notifier).
- **Unverified on a device**: see docs/ANDROID.md.

## D20b - Real E2E suite, dev-server proxy switch
`e2e/` (Playwright) covers the main flows in he-RTL mobile, en-LTR mobile and en desktop (docs/E2E.md). `server/src/devServer.ts` (dev/E2E only) gained `TRUST_PROXY=1` so each test can present its own client IP; the production per-IP registration limit is unchanged. The suite fails on unexpected browser console errors.

## D21 - Final hardening pass (release review)
Defects found by reading the code added in the last sessions, each reproduced by a test first (`server/test/hardening.test.ts`, `client/src/sw/sw.test.ts`, `client/src/api/identity.test.ts`, plus extensions of the existing suites):
- **Account deletion returned 500** whenever the client's `Idempotency-Key` was sent (it always is): the replay record was written for a user that no longer existed. The record is now only stored while the user row exists. In Device Mode that 500 also skipped the re-provisioning of the hidden account, leaving the app without an account. Deleting an account now also removes the login/registration counters keyed by the username hash.
- **Quota and lockout races**: AI quotas (`message`, `photo`, `translate`) are charged in one transaction that locks the user row (`reserveQuota`), so a burst of parallel requests can no longer exceed them; a failing provider still costs a charge. Login failure counters are created before they are locked (no unique-key 500), a correct password gets no session (and the same 401 a wrong one gets, never a 429 that would single it out) if parallel guesses locked the name while it was being hashed, and a burst of registrations cannot pass the per-address limit. Known residual: guesses already being hashed when the first lock lands are still evaluated (bounded by the IP limiter and the PBKDF2 thread pool).
- **Coach safety shield**: bypassed by spacing ("k i l l  m y s e l f"), accents, zero-width characters, look-alike letters, leetspeak, stretched letters and, most seriously, by an earlier negation in the sentence ("there is no point, I want to die", "אין טעם, אני רוצה למות"). A negation now only counts in the same clause, with no first-person subject in between, and for self-harm only when directly adjacent. Extra spellings are tried in addition to the plain one, so they can only add hits (D7). Known residual: a word split by one space inside ("ch est pain").
- **Prompts**: a free-text language name was written into the coach and translate system prompts. Standard codes now use the server's own English name (the client's is ignored); `x-` names must be at most 4 words, pass the safety classifier and are quoted as data; otherwise 400 `invalid_language` (translate) or ignored (coach). Coach calls are capped at 600 output tokens and 2000 characters, and a minors clause forbids calorie/weight/1RM talk (the rules coach answers those with a redirect). Translation output with control or bidi-override characters is rejected.
- **Hosted web server**: CSP (all `'self'`, `data:`/`blob:` for images/media, no external host, so dish photos and clips need no relaxing), nosniff, frame-ancestors none, referrer/permissions policy, HSTS when the request is HTTPS, `Cache-Control: no-store` on `/api`. A missing build file (`/assets/*.js`, `/media/*.mp4`, ...) is now a 404 instead of the app shell with status 200, which the service worker used to cache as that file.
- **Service worker**: `lupu-shell-v2`; the offline identity copy is wiped on login, register, logout, account deletion, any 401, a different user id, and a 404 profile; answers already in flight at that moment are not stored; "keep me signed in" off keeps no offline copy at all; only real video/image responses are cached as clips; Range handling covers suffix ranges and 416; only a good HTML page is kept as the offline shell; the build-file part of the shell cache is bounded.
- **Shared devices**: the API layer tracks the signed-in user id. A different person signing in (or a sign-out / account deletion) wipes the per-person localStorage keys (`lib/userState.ts`), empties the query cache, cancels the previous person's reminders, and the offline outbox only shows and replays its own user's items (a 401 now pauses the outbox instead of marking items rejected).
- **Smaller**: malformed cookie escape no longer 500s; parallel registrations of one name give 409; impossible dates and out-of-range values are 400 (PostgreSQL class 22 maps to 400, unique violations to 409) and `IsoDateSchema`/backup timestamps are real dates; replacing a foreign session-exercise id is 404 (was a 409 existence oracle); restore stores no 1RM estimate for minors and progress/history hide stored ones; media URLs must be same-origin paths; expired sessions, old replay records and idle brute-force counters are pruned in small batches on sign-in; a stored translation can never write to `Object.prototype`; the reminder runtime serialises native calls and the newest wins (a logout can no longer be overtaken by a schedule in flight); an explicitly empty set of training days is respected; an unfinished workout from an earlier day no longer counts as "trained today".
- **Residual risks (not changed)**: whoever registers a name listed in `ADMIN_USERNAMES` first becomes admin (register it right after the first deploy, or leave the list empty: only the media admin API uses the role); lockout is per username and per address, so a known username can be kept locked by someone who keeps failing for it (accepted trade-off, 30 s doubling to 1 h); IP and username hashes in `auth_attempts`/`ip_hint` are unsalted and brute-forceable for IPv4; the restore endpoint accepts up to 8 MB of JSON per call without its own rate limit; the AI cost ceiling is per account (30 translate calls/min, 150/day) and accounts are free.

## D22 - Version 10 is server-free (Device Mode is the product, proven without a network)
- **Decision (user request: "version 10 without a server")**: the Android app is the Device Mode build (the portable API core in a Web Worker over PGlite/IndexedDB, hidden local account, `VITE_RUN_MODE=device`). Nothing about the app needs a server. The hosted build stays in the repository unchanged for web hosting.
- **What still needs the internet (and only this)**: (1) barcode lookup, an optional feature: a direct HTTPS GET from the worker to `world.openfoodfacts.org` (`/api/v2/product/<number>.json`; the number is the only datum, Open Food Facts also sees the IP address). Offline or failing, it says so once in plain words and never blocks anything (search, quick add and "new food" stay). (2) the optional AI proxy, only in a build with `VITE_AI_PROXY_URL` (host = that URL; the shipped AAB sets none; D19's proxy requirements still hold). The egress guard in `deviceWorker.ts` allows exactly: the app's own origin, `world.openfoodfacts.org`, and the proxy host.
- **What never does**: first launch and all of: onboarding, workouts and live sessions, plans, nutrition logging and menus, coach (rules), progress, reminders (local notifications), export/restore/delete, fonts, icons, manifest, 244 clips, dish photos, language switching. `e2e/device` runs all of it with every non-localhost host unresolvable and fails on any off-origin request, any `/api` request, any failed request or console error. A scan of the built files finds no http(s) reference except Open Food Facts and namespace/documentation strings.
- **Without AI the UI does not offer AI**: `AI_AVAILABLE = !IS_DEVICE || VITE_AI_PROXY_URL` (`client/src/env.ts`). Hidden: the photo-estimate tile and the "translate the app to another language" sheet (replaced by one honest line: Hebrew and English are built in). The coach is the rules coach with one neutral note ("runs on this device, nothing is sent"); there is no "AI unavailable" error path. Hosted behaviour is unchanged.
- **Honest copy**: Device Mode wording overrides live in `i18n/features/deviceCopy.ts` as `dev.<key>`; `lookup()` prefers `dev.<key>` when `IS_DEVICE` (hosted never reads them, a unit test checks every override has a target and the same placeholders, `dev.`/`legalDev.` are never machine translated). The privacy policy and terms of the device build are separate documents (`features/legalDevice.ts`, `legalDev.*`): no account, no operator, no cloud, backups are the files the person exports, the only network use is the barcode number, AI paragraphs (`a1…`) appear only when an AI proxy exists. "Delete account" is "Delete all data", the data-deletion page, the errors ("Server error", "sign in again", "session expired") and the backup copy are device versions. The e2e honesty scan walks welcome, every onboarding step and every route in he and en and fails on account/server/sign-in/sync words outside sentences that state their absence. The export file no longer contains the hidden local identifier (`extra.account` is null in Device Mode).
- **Bugs found by the new e2e and fixed**: (1) airplane mode: TanStack Query's default `networkMode: 'online'` pauses every query and mutation when `navigator.onLine` is false, so the workout summary was blank (a paused query has no data and no error) and `useOnline()` blocked "Finish workout" and showed "will sync later" banners on a phone with no server to sync with. Device Mode now uses `networkMode: 'always'` and `useOnline()` is true; raw connectivity (`useNetworkOnline`) is only used for the barcode note. (2) `ExerciseVideo`: the autoplay effect did not re-run when the `<video>` element appeared after the clip list loaded, so clips did not autoplay and the Play button did nothing (not Device Mode specific, but it hid the packaged-media check). (3) Wi-Fi-only video, the video-cache and "waiting to sync" panels are meaningless on a phone that ships the clips: hidden in Device Mode (`autoplayAllowed` ignores the Wi-Fi preference there). (4) The service worker is no longer registered in the Android app (it duplicated up to 300 MB of packaged clips into the Cache API and could serve stale files after an update) and a start-up step removes the registration and `lupu-*` caches older builds left (`lib/serviceWorker.ts`).
- **Known limits**: ~~restore brings back workouts, food log and weights only~~ (fixed in D23: the backup is now complete); the database is not encrypted (the Android sandbox and screen lock are the protection; the policy says so); a backup file is plain JSON. Not run in a real Android WebView.

## D23 - The backup file is complete: export everything, restore it all (backup format 2)
- **Why**: in Device Mode the exported file is the only way to recover data (new phone, "delete all data", cleared app data). Until now `/api/export` carried plans, saved meals, own foods, coach chats and the profile, but `/api/device/restore` brought back only workouts, food log and weights, so a phone change silently lost the rest.
- **File format**: `{ backup, extra, clientSettings? }`. `backup.version` is 2 (`BackupV2Schema` in `shared/src/schemas.ts`); version 1 files are still read (`BackupV1Schema`); any other version is refused by name (`newer_version` for a file from a newer app, `unsupported_version` otherwise) before anything else is looked at. `backup` holds: `exportedAt`, `appVersion` (build version, `Deps.appVersion`), `mode`, `profile`, `bodyWeight`, `readiness`, `foodLog`, `savedMeals` (+ items), `customFoods`, `plans` (+ day structure), `sessions` (name, source and plan link, sport, times, duration, local date, readiness, XP awarded, exercises with finisher flag and prescription, sets with time done), `personalRecords`, `xpEvents`, `achievements`, `notifications`, `coachThreads` (+ messages with role, provider and `safetyCategory`). Every row uses the limits of its write route, and the export is checked against the restore schema before it is handed out (500 `export_unrestorable` rather than a file that cannot be restored). `extra` is only `{ account }` (hosted: whose file it is; null in Device Mode) and is never restored. `clientSettings` is written by the CLIENT (`components/profile/clientSettings.ts`): a typed block, not a dump of `lf_*` keys: theme, language (he/en), remembered sport, video options, ready-workout filter, menu choices, shopping check-offs and the reminder settings. Never in it: `lf_username`, `lf_last_uid`, `lf_ephemeral`, the live workout and rest timer, onboarding draft, backup-reminder state, custom-language cache. Per-person values (reminder settings, remembered sport) are exported without the user id and re-keyed to the person restoring. The block is never sent to the server; the client applies it after the data is in, and a damaged block is dropped without blocking the restore.
- **Never exported**: password hash, sign-in sessions and tokens, CSRF tokens, `auth_attempts`, idempotency/replay records, AI quota counters (`coach_usage`, which also hold the translation ledger), reset tokens, the hidden device username.
- **Policy: REPLACE, all or nothing**. One transaction (`services/backup.ts`, `restoreBackup`): every section the file carries replaces what is stored; a section the file does not carry is left exactly as it is (a version 1 file has no plans, saved meals, own foods, check-ins, chats, XP; the result lists them under `untouched`). A version 2 file carries every section (a missing one is a validation error, so a truncated file can never wipe data). The UI states this before the person confirms, and again in the result. Restoring the same file twice therefore gives the same data (tested). Rows get new ids; old workout and plan ids only connect XP events and plan links to the restored rows. Any database error rolls everything back (400 for data errors such as a NUL character; tested by fingerprinting every table before and after). Set-based inserts (1,000 rows per statement via `jsonb_to_recordset`), `SET LOCAL statement_timeout = 120s`, one restore per person at a time (advisory lock), at most 2 at once per process, at most 6 per person per minute (`RESTORE_PER_MIN`), body cap 8 MB hosted / 200 MB device. Sign-in and CSRF are unchanged (401/403); the route has no target argument, so it can only ever write the caller's own rows (other people's ids in a file collide with nothing: ids are regenerated).
- **Durability (found by the device E2E)**: with PGlite over IndexedDB a restore could be answered before its files were written (`PGlite.syncToFs` returns at once when another sync is already queued), so reloading the app right after "Backup restored" sometimes showed the old data (about 1 run in 4). `DbAdapter.flush?()` (PGlite: a direct filesystem sync) is awaited by the restore route after the commit, so the answer means the data is on disk; a unit test pins it and 14 consecutive delete-all -> onboarding -> restore -> immediate reload cycles in the real build kept the profile every time (before: lost in 1 of ~6). Other writes keep the old behaviour (a lost food entry is recoverable, a lost restore is not).
- **Derived data is not trusted**: personal records are recomputed from the restored sets with the same rules as finishing a workout and can only be RAISED by the file's records (a record outlives the workout it came from); XP events are accepted only when the restored data still backs them (a workout day with a finished workout, a `sets`/`pr` event with a restored workout and a plausible amount, a food day with two meals, a protein day with food, a weigh-in week with a weigh-in, a weekly goal week with a workout; exact amounts; duplicates and unknown types dropped and counted in `skipped.xpEvents`), so a hand-edited file cannot mint XP; readiness state is recomputed from the answers; achievement ids must be known (a badge a file claims for an id this app knows is kept: badges are cosmetic and never gate anything; residual risk below). Plans: unknown exercises are dropped and counted, at most one plan is active, an archived plan is never active. Own foods obey the 100 g macro rule. Workouts keep their local date, duration and plan link (re-pointed at the restored plan). Unfinished workouts are skipped and counted (a workout in progress lives in the live screen of that phone). Food entries and chat messages keep their order (consecutive timestamps).
- **Minors**: minor rules are re-applied however the file got here. A restore never turns a minor's account into an adult one (the file's profile is skipped and `skipped.profile` says so); a file whose profile is a minor's makes the account a minor's; either way no 1RM estimate is stored (tests in `server/test/backup.test.ts` and the existing hardening test). The coach safety shield is re-run over restored chat messages: an unflagged message that the shield catches is flagged on the way in, with the reply after it, so it never reaches an AI provider.
- **Result summary**: `{ ok, policy: 'replace', backupVersion, restored: { workouts, sets, foods, weights, plans, savedMeals, customFoods, threads, messages, readiness, personalRecords, xpEvents, achievements, notifications, profile }, skipped: { profile, unknownExercises, unfinishedWorkouts, duplicateDays, invalidItems, xpEvents, achievements }, untouched: [...] }`. The panel shows it in plain words (he + en), the confirmation sheet lists exactly what will be replaced, with counts, and errors are specific: not JSON, not a LUPU-FIT backup, made by a newer app (names the format), damaged at a given place, too large (names the limit), rejected by the server.
- **Not restorable, on purpose**: the account/username (there is none in Device Mode; hosted keeps its own), password and sessions, replay records and AI quota counters (operational; restoring a quota would also let a restore reset a limit), the live workout in progress, the backup-reminder timestamps, the custom-language cache (it is regenerated by the translate feature), and anything stored outside the app (Android notification schedule: reminders are re-armed from the restored settings on the next start).
- **Residual risks**: (1) achievements a file claims are not re-derived, so a hand-edited file can show badges (XP cannot be forged; in Device Mode the person owns the database anyway); (2) on a phone with no profile yet the restore button sits in Profile, so the new phone needs the short onboarding first, then Restore replaces the profile; (3) an export that cannot satisfy its own schema (data that predates a limit) fails loudly instead of producing a partial file; (4) a backup is plain JSON, the person is told to keep it somewhere safe; (5) not run in the real Android WebView: whether `<a download>` and the Web Share API hand the file over there is untested (docs/ANDROID.md).
- **Tests**: `server/test/backup.test.ts` (37: full round trip with every data kind, replace and idempotency, version 1, hostile and oversized files with a fingerprint of every table, rollback after a late database error, minors, isolation between people, derived totals, chunking), `client/src/components/profile/{backup,clientSettings}.test.ts`, `client/src/pages/Profile.test.tsx`, `client/src/device/deviceCore.test.ts` (export -> real "delete all data" wipe -> restore on the on-device database), `e2e/device/f-profile-backup.spec.ts` (real browser build: plans, saved meals, own foods, coach chat, profile and food survive export -> delete all data -> onboarding -> restore, restoring twice changes nothing, wrong/damaged/newer files refused).
