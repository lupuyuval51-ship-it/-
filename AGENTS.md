# LEVEL UP engineering notes

Stack: Next.js 16 (App Router) · React 19 · TypeScript · Tailwind 4 · React Three Fiber · PostgreSQL + Prisma 7 · Zod 4 · Stripe.
Node ≥ 20.9. Commands, configuration and architecture are in `README.md`.

## Rules that are enforced (and tested)

- `PLANS_ENABLED` (default `false`, `src/server/env.ts`) switches the whole plan layer: off = no plan, price or pricing page is shown, checkout is a 404 and every account resolves to the full product (`computeEntitlement`); on = Free/Plus/Pro. The code stays; the test suites run with it on, `tests/integration/plans-off.test.ts` covers the off switch. `PLANS_SHOWN` (default `true`) keeps the plans and prices visible as information on the website while they are off (no checkout, no payment banner). The Android app hides plans and prices altogether (`showPlans()` in `mobile/src/features.ts`, on only with `VITE_SHOW_PLANS=1`); its `#/plans` page and the questionnaire's plan step stay in the code, never with a buy button or payment link.
- Plans, prices, allowances and graphics permissions live **only** in `src/config/plans.ts`. Never gate by price in the UI; the server enforces.
- Plan features and quotas (AI robot level, AI edits per period, version history) are in `src/config/plans.ts` (`features`) and enforced only on the server
  (`src/server/games/ai-edit.ts`, `versions.ts`). An AI edit reserves a quota slot (`AiEdit` PENDING) and commits it with the new version in one transaction;
  a failed edit never costs anything. The model edits a game only through the allow-listed operations in `src/lib/game/spec/edit.ts` and the result must pass `validateGameSpec`.
- The allowance is a **separate quota of games per level** per period (`PLANS[plan].allowance`); using one level never reduces another: Free A not available (paying plans only), B 1, C 5 per UTC calendar month; Plus A 3, B 5, C unlimited per billing period; Pro A 5, B 10, C unlimited per billing period. `UNLIMITED` (null) = never refused by a count (still counted; one job at a time and the `generate` rate limit still apply). With plans off everybody gets Pro's quotas per calendar month. Read it only through the helpers (`levelsAllowed`, `quotaOf`, `quotaLeft`, `planOffer`, `defaultLevel`); every "N topics at level X" text is generated from `planOffer`, never typed.
- Every game has a **feature tier = level** (C = 40 %, B = 70 %, A = 100 % of `GAME_FEATURES`) decided by the server per game: the request's optional `level` is only a wish, checked against `levelsAllowed(plan)` (403 `FEATURE_TIER_LOCKED`) and that level's games left (402 `ALLOWANCE_EXHAUSTED` with level, left and `resetsAt`; default: the highest level that fits the request and still has a game left); EXTEND keeps the game's own level and uses one game of it; AI and manual edits stay within the game's level. It is enforced on the saved game by `clampToFeatureTier` and on requests by `assertRequestAllowed` — never in the UI. Integration suites run at tier A through `setFeatureTierForTests` (`tests/integration/setup.ts`, where every plan makes only that level, with the plan's largest counted quota: Free 5, Plus 5, Pro 10); `feature-tier.test.ts`, `plans-off.test.ts` and the per-level tests in `allowance.test.ts` use the real levels and quotas.
- Boss battles are made of ordinary challenge stations (no separate grading): phases open in order, the validator plays the game with the real progress rules
  (`crossCheck` in `src/lib/game/spec/validate.ts`), and `PlayState.bossesDefeated` may be missing in older saves (always `?? []`).
- Plus and Pro have the **same** Tier A graphics; Free gets Tier B/C. The tier is resolved on the server from the persisted plan, never taken from the client.
- Allowance games are **reserved → committed/released** per level in the database (`AllowanceQuota`, atomic conditional update `used + reserved + 1 <= limit` for the job's own level `GenerationJob.featureTier`, idempotency key, one in-flight job per user, settle-once per job, the reaper). An upgrade or downgrade inside a period refreshes the limits and keeps what was used per level. A failed generation must never cost anything.
- Game score, rewards, hints, attempts and completion are calculated **server-side from validated events**. The browser never receives answer keys, explanations or solutions before the server releases them.
- A payment never activates access unless it arrives through the verified billing pipeline (`src/server/billing`): Stripe signature verified over the raw body, idempotent by event id, price checked against the plan config. The dev simulator (`PAYMENTS_MODE=dev`) goes through the same pipeline, is labelled, and is refused when `APP_ENV=production`.
- Sign in with Google (`src/server/auth/google/`, `docs/google-signin.md`): exists only when `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` are both set. Identities are keyed by Google's `sub` (`AuthIdentity`), `email_verified` is required, an
  existing e-mail is **never** auto-linked (the owner links Google from the account page after a password sign-in), the last way to sign in can never be removed, and a Google-only account (no usable password) confirms
  deletion with a fresh Google re-authentication of the same session. The redirect URI comes from `APP_URL`. The Android app uses Supabase's Google provider behind `VITE_GOOGLE_AUTH=1`; no secret is ever in the app.
- Minor profiles are private by default. No open chat and no precise location (the region is a user-chosen billing region only).
- Hebrew/RTL is the default and English/LTR must stay functional: add every string to both dictionaries (`defineDict` fails the build on a missing key), use logical Tailwind properties (`ms-`/`me-`/`start-`/`end-`). Spanish (LTR) is a third interface language: every key also goes in `src/lib/i18n/dict/es/*.ts` (typed against the English keys; `tests/unit/i18n-spanish.test.ts` checks keys, placeholders and that it is really translated). Learning content stays Hebrew/English: use `contentLangOf(locale)` wherever a UI locale picks content (Spanish → English).
- Demo templates are never presented as AI output: games store `generatorKind` and the UI shows the label.
- No secrets in the client: no `NEXT_PUBLIC_*` variables, no keys in props. `.env` is never committed.
- Topic library (`src/lib/game/topics`): curated, fact-checked he+en content per topic and level, built without any model and labelled `catalog` / “Topic library”, never AI. Each topic is its own lazily imported module (literal `import()` in `loaders.ts`; never in a first chunk); the catalogue lists only topics whose content exists; `topicId` is only a catalogue key. Same validation, tier clamp, phone fit and allowance as every game; `tests/unit/topics.test.ts` must stay green (count, hygiene, every topic × level builds and finishes). Two parts: the original library (`catalog.ts`, 210 topics) and the **Plus and Pro collection** (`catalog-plus-pro.ts`, 260 topics, 20 to 30 per category, written in batches of ten, each fact-checked by a second reviewer, and held to a stricter bar: 8+ items per level, explanations of 40+ characters, the right answer the longest option in at most 40 %, no `<` or `>` in Hebrew; `scripts/check-topics.ts` checks and builds new content before it is listed). Tiers live only in `src/lib/game/topics/premium.ts`: in the original library about a third of every category is not free (two topics per category **Pro only**, the rest of that third **Plus or Pro**); the collection is never free (in every category half the topics are **Plus or Pro** and half, the more advanced ones, **Pro only**: 130 and 130); each topic has a tier (`topicTier`: free / plus / pro) and a plan plays the tiers listed in `features.topicTiers` (`src/config/plans.ts`, never gate by anything else). The server refuses a locked topic with 403 `TOPIC_LOCKED` (`details.requiredPlan` = the cheapest plan that opens it), the offline generator with `TIER_LOCKED`; the picker only shows the lock. With plans off everybody resolves to Pro, so nothing is locked. `tests/unit/premium-topics.test.ts` checks every topic against every plan.
- Display switches (they never unlock anything; the server still enforces every rule): `GAME_EDITING` and `DEMO_TEMPLATES` (`src/server/env.ts`, default `false`, the test suites switch them on, `tests/integration/display-switches.test.ts` covers them off). Off, the game page hides the editing tools (manual edits, AI edit robot, version history; the API stays), and without an AI provider a subject alone is refused with 422 `MATERIAL_REQUIRED` before anything is reserved (material or a library topic is needed). The app has its own (`mobile/src/features.ts`: plans, and demo games from a subject without notes), both off.
- Courses (`src/lib/game/topics/courses.ts`): a few topic-library topics taught in order as chapters — today one course, "Fractions, decimals and percentages" for grades 5–6, 9 chapters (`course-fractions-1…9`). A chapter is an ordinary topic (marked `course` in the catalogue) with a lesson (`TopicContent.l`: one or two paragraphs, a worked example and a hands-on task, he+en): the game puts the lesson boards in the first area behind the mission `m-1-0`, which every question waits for, and the task at the end. Chapters are free on every plan and not counted in a category's paid third. `tests/unit/course-content.test.ts` holds them to a stricter bar (8+ items per level, explanations of 50+ characters, the right answer the longest option in at most 35 %, no `<` or `>` in Hebrew). The app's home screen and `#/course/<id>` (`mobile/src/pages/Course.tsx`, progress from the games on the phone in `mobile/src/course-model.ts`) lead through it; `tests/e2e-mobile/course.spec.ts` covers the flow.
- Maths inside a Hebrew line is drawn left to right (`MathText`, `src/lib/i18n/bidi.ts`) in challenges, explanations, hints, the review screen and lore boards. Write a blank as `x` (`1/3 = x/9`), never `?`, and never `<` or `>` in Hebrew text (a right-to-left line mirrors them).
- AI output is untrusted: it must pass `validateGameSpec` (schema, cross-checks, solvability, sanitising) before it is stored or played. Nothing in a spec is executable.

## Offline Android app (`mobile/`, `android/`, `src/lib/offline`)

- A deliberate, documented exception: no server, so the reducer, answer keys and scoring run on the device. Never import server
  code (`server-only` throws in that bundle). No payments and no AI keys in the app. The only AI in the app is LEVEL UP AI, an explicit option of the create screen for a signed-in learner (`mobile/src/cloud/ai.ts`): it calls the Edge Function `generate-game` of the separate Supabase project `levelup-ai` (`src/server/ai/edge/`, the key lives only in that project's secrets), the answer must pass `validateGameSpec` on the phone and carry the `ai` label before it is saved, and CSP `connect-src` lists exactly the account project and that one URL.
- Optional account + cloud backup through Supabase (`mobile/src/cloud`, `src/lib/offline/sync.ts`, `supabase/`): only the URL and
  the *publishable* key are in the app; every table is owner-only (RLS, tested by `supabase/tests/rls_checks.sql`). Signed out,
  the app makes no network request (tested). CSP `connect-src` lists exactly `'self'` and the project URL — never `*`.
  Schema changes go through `supabase/migrations/`; re-run the Supabase security advisor afterwards.
- Paid features there must use Google Play Billing, never Stripe. Generated games must still pass `validateGameSpec` and keep their `generatorKind` label.
- Feature tiers apply on the device too: `generateOffline(…, tier)` refuses what the tier lacks (`TIER_LOCKED`) and clamps the rest with `clampToFeatureTier`; the tier comes from `src/lib/offline/entitlement.ts`, which stays at full tier A until Google Play Billing supplies the purchased plan.
- Games made on a phone are fitted to a touch screen by `fitForDevice` (`src/lib/game/spec/device.ts`): less walking, easier jumps, no moving platforms, milder hazards, more time for timed answers, fewer collectibles — never a change to challenges, answers, missions or bosses, and the result is re-validated. The request's `device` field is only a hint (it can never unlock anything); the Android app always sends `"phone"`, the website's create form sends it for small touch screens, and the AI is told about it in the prompt.
- Play release: `docs/play-release.md` (target API, privacy/backup settings, Data safety answers, checks on the built AAB) is guarded by `tests/unit/android-shell.test.ts`; keep both in step when changing `android/` or the CSP.
- First launch of the app (`mobile/src/pages/FirstSetup.tsx`, `src/lib/offline/first-run.ts`): a full-screen 3-step questionnaire shown before anything else (App.tsx renders it instead of every screen until it is done or skipped) — language (English preselected; Hebrew, Spanish), topic interests (topic-library categories), minutes per day. With `showPlans()` on (off in a normal build) a 4th step asks the country for prices (a user choice kept on the phone, never a location) and the plan the learner wants (a preference only: the app sells nothing, no buy button, no payment link). The answers stay on the phone and are used only to suggest: the topic picker opens on the first interest, 20+ minutes a day proposes a full adventure. Then the welcome; Settings can change the language and re-open the questions. Existing installs skip it. The `e2e` build keeps Hebrew and skips it; `tests/e2e-mobile/first-setup.spec.ts` covers the flow.
- Main navigation is the bottom tab bar (`mobile/src/pages/TabBar.tsx`: home — which opens with the learning-path card —, new game, review, settings; 56 px tabs above the system bar; hidden on the play screen and during the questionnaire). Screens keep bottom padding so nothing ends under it.
- Run `npm run test:e2e:mobile` for changes that affect it.

## Working agreements

- Before calling work done run `npm run check` (typecheck + lint + unit/integration) and, for UI/gameplay/billing changes, `npm run test:e2e`. Report what was actually run; never claim an unrun test passed.
- Integration tests use the `levelup_test` database; never point them at real data.
- Changes to the database go through a Prisma migration (partial indexes / CHECKs are hand-written in SQL).

## Removed on purpose

The previous version of this file described the archived prototype that lived in `legacy-demo/` (removed; still in git history) (dependency-free Node runtime, a BASIC tier, "Daily 3D Quest",
manual bit payments approved by an admin, private proof files). The LEVEL UP rebuild specifies a different stack and exactly three plans
(Free / Plus / Pro) with Stripe billing, so those rules no longer apply and were dropped rather than kept as dead guidance.
